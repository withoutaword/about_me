## 我建议以后每一个重要 Case 都统一采用 6 层结构

你现在这篇已经隐约形成了，可以进一步标准化：

|层|回答的问题|
|---|---|
|**Context**|当时系统是什么状态？|
|**Constraint**|什么真实问题让旧设计失效？|
|**Decision**|我做了什么架构决策？|
|**Trade-off**|为什么这样做，而不是其他方案？|
|**Implementation**|核心技术机制是什么？|
|**Evidence**|数据证明结果怎么样？|

比如你的 Agent Skill：

**Context**

工程团队负责 benchmark adaptation，一个 benchmark 大约需要 2 天。

**Constraint**

Benchmark 数量增加、业务快速变化，工程团队成为瓶颈。

**Decision**

不是简单增加人力，而是把 extension boundary 标准化，然后让 Agent 操作这个稳定接口。

**Implementation**

```text
Specification
     ↓
Examples
     ↓
Integration Skill
     ↓
Code Generation
     ↓
Tests
     ↓
Review Skill
     ↓
Human Approval
```

**Trade-off**

Agent 不直接修改 arbitrary core logic，只允许在标准 extension point 工作。

**Evidence**

```text
Integration lead time
2 days → ~10 minutes

6+ reusable Skills

Human engineering approval retained
```

这就是非常漂亮的 Architecture Case。
