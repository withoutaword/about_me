Recommendation systems rarely begin as platforms. A team builds a model, connects the required features, adds preprocessing, and exposes an inference path. The result solves an immediate business problem, and that is often the right decision at the time.

The difficulty appears when the same pattern is repeated across products. Each business gradually accumulates its own feature retrieval, transformation, model-input assembly, and deployment logic. What began as a direct path to production becomes a collection of parallel pipelines that are expensive to change and difficult to keep consistent.

I contributed to the architecture and engineering of a configuration-driven recommendation platform that addressed this problem through shared feature and model serving. The goal was not to eliminate all variation. It was to identify which parts should become stable infrastructure and which parts should remain configurable.

![From hard-coded pipelines to configuration-driven infrastructure](/project/image/recommendation-transformation.svg)

## 1. Repetition Was the Architectural Signal

The original systems were optimized for individual deliveries. A typical recommendation application owned the entire serving path:

```text
retrieve features
      ↓
apply transformations
      ↓
assemble model inputs
      ↓
load and invoke the model
      ↓
return prediction results
```

This design was understandable for one model and one business. At scale, three problems emerged.

### Feature and model logic became coupled to business services

Every new feature or model could require application code changes, validation, performance testing, and redeployment. As models became more complex, inference workloads also competed with ordinary business logic for CPU and memory.

### Offline and online definitions could drift

Training and serving systems maintained related definitions through different paths. Manual synchronization made it possible for a model to train with one feature interpretation and serve with another.

### Teams repeated similar engineering work

Different products rebuilt variations of the same feature access, preprocessing, deployment, and inference mechanisms. Local delivery remained possible, but organizational delivery became slower.

The repetition was not merely duplicated code. It showed that a shared architectural layer was missing.

> **When many teams repeatedly solve the same integration problem, the next unit of improvement may be a platform rather than another implementation.**

## 2. Configuration Became the Control Plane

Moving logic out of business services was not enough. Without a common contract, shared services would simply centralize the existing inconsistency.

The platform therefore started with a unified model–feature configuration: an explicit definition of which features a model required, how those features were represented, and how the online input should be assembled.

![Single source of truth for offline and online systems](/project/image/recommendation-single-source.svg)

This configuration acted as a control plane for both offline and online workflows. Instead of coordinating several independent definitions, teams could register a model and its feature contract once, then allow platform components to interpret that contract consistently.

The important shift was conceptual:

```text
Before: behavior distributed across application code
After:  stable serving engines interpreting versioned configuration
```

Configuration did not remove code. It moved common variation into a form that could be reviewed, validated, versioned, and reused.

## 3. Separating Feature and Model Serving

The platform divided the serving path into two reusable capabilities.

### Feature as a Service

Features were registered with metadata such as source, type, shape, default handling, and approved sharing rules. A recommendation workflow selected a feature set by configuration; the shared service resolved retrieval and transformation through a stable interface.

This reduced the need for every business application to implement feature plumbing. It also made feature reuse visible and governable instead of allowing similar definitions to diverge silently.

### Model as a Service

The model-serving layer standardized registration, deployment, loading, warm-up, health checking, prediction, scaling, and rollback. Business services referred to a business and model identity instead of embedding runtime-specific deployment behavior.

![Feature-as-a-Service and Model-as-a-Service flow](/project/image/recommendation-faas-maas.svg)

The separation mattered because features and models evolve at different rates. A reusable feature set may serve several models, while a model version may change without requiring feature infrastructure to be rebuilt. Independent contracts allowed each side to evolve without coupling every change to the entire recommendation application.

## 4. One Interface, Different Compute Resources

Recommendation workloads do not have a single ideal runtime. Simpler models can run efficiently on CPU. More complex models may require GPU acceleration to reach acceptable latency and throughput.

The platform kept feature processing resource-neutral and selected the model runtime through deployment configuration. A proxy layer hid CPU- and GPU-specific invocation details from business applications.

![Configuration-driven recommendation platform architecture](/project/image/recommendation-platform-architecture.svg)

This gave consumers a stable prediction interface while allowing the platform to evolve its resource strategy. It also prevented the CPU and GPU paths from becoming two independent application architectures.

## 5. Peak Performance Was Not the Only Objective

One of the most useful lessons came from GPU inference.

An early path converted training models through ONNX into TensorRT and served them through an optimized runtime. The approach could improve hardware efficiency, but unsupported operators required extra development, and every conversion step increased the cost of model iteration.

For applicable workloads, the platform later adopted a multi-process TensorFlow Runtime with GPU partitioning. This provided a different balance: stronger compatibility with frequently changing models while still improving GPU utilization.

![GPU inference architecture trade-off](/project/image/recommendation-runtime-tradeoff.svg)

The decision could not be made from throughput alone. We had to consider:

- runtime performance and latency;
- model and operator compatibility;
- conversion and maintenance effort;
- debugging complexity;
- deployment frequency;
- the time required for an algorithm change to reach production.

> **The fastest runtime is not always the fastest engineering system.**

For a research-heavy workload, reducing conversion friction can create more total value than maximizing isolated benchmark performance.

## 6. Platform Value Had to Be Measured End to End

Infrastructure work can look successful while merely moving effort from one team to another. We therefore evaluated the platform through delivery and runtime outcomes, not only service availability.

Across the implemented scenarios, the observed results included:

| Area | Observed outcome |
|---|---:|
| Feature iteration | Approximately 2 person-days → 5–30 minutes |
| Ordinary model deployment | Approximately 4 hours → 30 minutes |
| Concurrent experiments | 5 → 20 |
| Complex-model inference | Approximately 5.2× QPS in performance testing |
| Infrastructure cost | Approximately 75% estimated reduction in the measured workload |
| Offline/online feature consistency | More than 99.9% across implemented flows |

These figures came from specific business implementations and measured workloads. They are evidence of the architecture's effect in those contexts, not universal guarantees for every model or traffic profile.

The most important result was that common feature and model changes no longer required every business to rebuild the full path independently.

## 7. What the Architecture Changed Organizationally

The platform changed more than deployment mechanics.

Algorithm teams could describe feature and model requirements through stable contracts. Business teams consumed prediction capabilities without owning resource-specific inference code. Platform engineers could improve scheduling, runtime utilization, observability, and governance behind shared interfaces.

That separation made ownership clearer:

- **algorithm teams** owned model intent and validation;
- **business teams** owned product behavior and integration requirements;
- **platform teams** owned reusable serving mechanisms and operational guarantees.

Clear ownership reduced coordination cost because every model change no longer required every participant to understand the complete implementation path.

## 8. Lessons That Continued into Later Platforms

Although this work focused on recommendation systems, several principles carried into my later Agent and evaluation platforms.

### Standardize before automating

Automation scales the structure it receives. Automating fragmented pipelines would have made inconsistency faster rather than eliminating it.

### Make variation explicit

Stable engines and explicit configuration are easier to reason about than repeated conditional logic scattered across applications.

### Treat consistency as a platform property

Offline and online alignment should be enforced by shared contracts and validation, not by hoping several teams synchronize changes manually.

### Optimize the engineering loop

Runtime QPS matters, but so do deployment time, compatibility, rollback, debugging, and experiment throughput.

### Measure adoption, not only architecture quality

A reusable abstraction becomes valuable when teams can use it without rebuilding the same infrastructure around it.

## Final Thoughts

The transition from hard-coded recommendation pipelines to shared infrastructure was not a move from code to configuration. It was a move from repeated local decisions to explicit platform contracts.

The architecture worked because it separated the stable mechanism from changing business definitions, aligned offline and online workflows, and allowed runtime choices to evolve behind a common interface.

That pattern remains useful beyond recommendation systems:

> **Find the repeated work, define the stable boundary, express variation explicitly, and optimize the complete delivery loop—not only the component benchmark.**
